## 1. Merge Conflict

- 어떤 상황에서 충돌이 발생했나요?

두 Branch에서 conflict.txt의 동일한 부분을 서로 다르게 수정한 후 git merge를 실행하자 Merge Conflict가 발생하였다.

- 충돌을 어떻게 해결했나요?

VS Code에서 Accept Both Changes를 선택하여 두 Branch의 변경사항을 모두 반영하였다. 이후 파일을 저장하고 git add와 git commit을 실행하여 충돌을 해결하였다.

## 2. restore

- `git restore --staged`와 `git restore`의 차이는?

git restore --staged는 Staging Area에 올라간 파일을 Staging에서만 내리는 명령어로, 실제 파일의 수정 내용은 유지된다.

반면 git restore는 Working Directory의 변경사항을 복구하는 명령어로, 기본적으로 Staging Area의 내용을 기준으로 파일을 되돌린다.

따라서 Staging 취소와 실제 파일의 변경사항 복구는 서로 다른 작업이라는 것을 알 수 있었다.

## 3. reset / revert

- `git reset --soft HEAD~1` 실행 후 변경사항은 어디에 남았나요?

git reset --soft HEAD~1을 실행하면 HEAD가 이전 Commit으로 이동하면서 가장 최근 Commit이 취소된다. 하지만 해당 Commit에 포함된 변경사항은 삭제되지 않고 Staging Area에 그대로 남는다.

따라서 Commit만 취소하고 수정 내용은 유지할 수 있었다.

- `git revert`가 `reset`과 다른 점은?

git reset은 HEAD를 이전 Commit으로 이동시켜 Commit 이력을 되돌리는 명령어이다.

반면 git revert는 기존 Commit을 삭제하지 않고 해당 Commit의 변경사항을 취소하는 새로운 Commit을 생성한다.

따라서 이미 공유된 Commit을 취소할 때는 기존 이력을 유지하는 git revert가 더 적합하다는 것을 알 수 있었다.

## 4. stash

- `git stash`와 `git stash pop`을 사용해 어떤 변화를 확인했나요?

git stash를 실행하면 Commit하지 않은 변경사항이 임시로 보관되고, 작업 중이던 파일이 이전 상태로 돌아간다.

이후 git stash pop을 실행하면 임시로 보관했던 변경사항이 다시 Working Directory에 적용되며, 정상적으로 적용된 경우 해당 Stash 항목은 목록에서 제거된다.

이를 통해 작업 도중 다른 Branch로 이동하거나 잠시 작업을 중단해야 할 때 stash를 활용할 수 있다는 것을 알 수 있었다.

## 5. 잘못된 Branch의 Commit 옮기기

- `cherry-pick`을 사용한 과정을 간단히 적어주세요.

`practice/es1206-wrong` Branch에서 `wrong-branch.txt`를 수정하고 Commit하였다. 이후 `git log -1 --oneline`을 통해 Commit Hash인 `a339e0e`를 확인하였다.

올바른 Branch인 `week3/es1206`으로 이동한 후 `git cherry-pick a339e0e`를 실행하여 잘못된 Branch에서 생성한 Commit을 현재 Branch로 가져왔다.

## 6. 실습 소감

- 가장 헷갈렸던 명령어 또는 문제 해결 과정:

Merge Conflict를 해결하는 과정이 가장 헷갈렸다. 처음에는 두 Branch에서 같은 파일을 수정했을 때 왜 충돌이 발생하는지 이해하기 어려웠지만, VS Code에서 충돌이 발생한 부분을 직접 확인하고 두 변경사항을 모두 반영하면서 해결 방법을 이해할 수 있었다.

또한 reset과 revert의 차이가 헷갈렸는데, reset은 HEAD를 이동시키는 방식이고 revert는 변경사항을 취소하는 새로운 Commit을 생성한다는 차이를 알게 되었다.

이번 실습을 통해 Git 오류가 발생했을 때 무조건 변경사항을 삭제하기보다는 현재 상태를 확인하고 상황에 맞는 명령어를 선택하는 것이 중요하다는 것을 배웠다.
